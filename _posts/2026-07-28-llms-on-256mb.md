### disclaimer:
i do not support generative ai as a replacement for human creativity, hyperscale ai datacenters, or models trained unethically on stolen data.
this experiment is none of that; it’s a constrained hardware test running a tiny offline model for engineering curiosity, pushing the hardware & also my skills to the limits.

## luckfox pico max

the luckfox pico max is a tiny little mcu that is actually a single board computer.

![luckfox pico pro/max](assets/img/luckfox-pico.jpg)

it runs an entire linux distro, (buildroot or ubuntu server,) on a cortex a7 cpu, 256 megabytes of ddr3l ram, a 1tops neural processor, 256mb spi nand flash & an sd card slot
meaning you could throw in a 128gb sd card in here and be done with it, but i've found with these devices it is best to run cheaper 32/64gb cards as they do tend to wear out after a while,
this is simply because of the amount of read/writes and sd cards do indeed have a lifespan.
using the nand flash would also be an advantage but alas, it is only 256mb and ubuntu server is... 674mb. so sd cards will have to suffice.

## setting up

my current setup is 3x pico max's, connected over ethernet via a 5port tp link gigabit switch, also connected to this switch is a wyse 3040 running debian as a "control core".

i will go into this cluster in more detail in the future. but for now lets get down to how i ran a large language model on a device that has less ram than a smartwatch.
you ~could~ treat this as a guide and follow, but alas the models i use are no longer available for public use.
this is more a record of a ridiculous experiment that somehow worked.

## compile llama.cpp

it will take for, ever. to compile on the luckfox.
it is best to clone it from a more powerful machine, cross compile using an arm toolchain and SCPing over the compiled binaries
but, keeping in theme with this ridiculous experiment i will be compiling directly on the luckfox pico max. :)

using llama.cpp and building from source:

```bash
sudo git clone https://github.com/ggerganov/llama.cpp
cd llama.cpp
sudo make LLAMA_NO_ACCELERATE=1
```

![llama.cpp uses new build system](assets/img/llm-cmake.png)

llama has changed its build system to cmake, so we make some changes:

```bash
mkdir build && cd build
cmake ..
make -j$(nproc)

```

as you can see, compiling on the luckfox pico max absolutely hammers it:

![cmake & btop](assets/img/llm-compile-btop.png)

100% CPU usage, but it's a great stress test. :)

### live compile notes 

- temp sitting at 55-58c
- no throttling events
- memory pressure is consistent but not fatal
- cmake progress is currently at 58% after 4 hours
- cpu is pinned at 75-100% usage depending on compile task

## why compile directly?

sure, it would be a lot faster to cross compile to arm on a more powerful machine, but the point here is to stress test hardware,
observe speed and thermals, as well as any failures on constrained hardware.

## tweaks and automation


i can tweak the model further by changing the cli command, although it wont make a massive amount of difference due to the hardware constraints 
but it will help slightly:

```bash
/opt/llm/bin/llama-cli -m /opt/llm/models/gpt-mini-q2.gguf --threads 1 --ctx-size 32 --top-k 20
```

ctx is how many tokens that is kept in memory, dropping it to 32 improves speed.
top-k is the probability, setting it to 20 tells the model to check only the top 20 logits.
fewer logits, fewer tokens which results in faster token generation.

i can go even faster with:

```bash 
llama-cli -m gpt-mini-q2.gguf --threads 1 --ctx-size 16 --top-k 10
```
which is the minimum possible using these flags.

ill also create a small swap for virtual memory but the pico max doesnt allow normal swapfiles, so ill have to use the userdata partition.

```bash
sudo dd if=/dev/zero of=/userdata/swapfile bs=1M count=256
sudo chmod 600 /userdata/swapfile
sudo mkswap /userdata/swapfile
sudo swapon /userdata/swapfile
```

and in /etc/fstab:

```bash
/userdata/swapfile none swap sw 0 0

```

to finish, i can automate the model too by simply creating a `.service` file at:

```bash
/etc/systemd/system/llm.service
```

then inside the unit file:

```bash
[Unit]
Description=Micro LLM
After=network.target

[Service]
ExecStart=/opt/llm/bin/llama-server -m /opt/llm/models/gpt-mini-q2.gguf --host 0.0.0.0 --port 8080 --threads 1 --ctx-size 32 --temp 1.0 --top-k 20
WorkingDirectory=/opt/llm
Restart=always
User=root

[Install]
WantedBy=multi-user.target
```

reloading systemd:

```bash
sudo systemctl daemon-reload
```

enabling the service:

```bash
sudo systemctl enable llm.service
```

and finally starting the service:

```bash
sudo systemctl start llm.service
```

checking service status:

```bash
sudo systemctl status llm.service
```

now the luckfox max will run this model as a service on each boot.

## insights

- compile will take forever on luckfox; cross‑compile elsewhere
- q2 model loads and runs, as does q6
- q3, q4, q5 and q8 refuse to load 
- small llm models like this output nonsense/garbage, but proof of concept is there 
- micro llms do run on a cortex a7 with only 256mb ram, just not very well in regards to coherence
